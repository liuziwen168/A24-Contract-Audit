## 1. 架构目标

以最少的服务实现可部署、可追溯的合同审核闭环：前端仅调用业务后端；业务后端负责认证、权限、任务编排和持久化；AI 服务仅处理文件与返回结构化审核结果，**不直接操作 MySQL**。

## 5. 分层设计与目录建议

业务后端分为 API、application（用例/任务编排）、domain（实体与规则）、infrastructure（SQLAlchemy、文件、AI客户端）层；AI服务分为 API、parser、ocr、pipeline、rules、llm、schemas 层。建议目录：

```text

storage/{uploads,reports}/
deploy/{nginx}/
docs/
```

## 6. 合同审核调用流程

```mermaid
sequenceDiagram
    participant F as Vue3前端
    participant B as 业务后端
    participant W as 后端任务执行器
    participant A as AI服务
    participant D as MySQL
    participant L as 法务审核员
    participant R as 风控审核员
    F->>B: POST /api/v1/reviews
    B->>D: 创建reviewRecord(pending/aiReview)
    B-->>F: 返回reviewId和状态
    W->>D: 领取任务并置processing/aiReview
    W->>A: POST /internal/v1/reviews/full
    A->>A: 解析、OCR、分类、抽取、风险、比对
    A-->>W: 结构化审核JSON
    W->>D: 保存不可变AI初审结果并置processing/legalReview
    L->>B: 法务首次业务写操作或确认
    B->>D: 同一事务自动领取legal_reviewer并追加修订/意见
    B->>D: 法务确认后置processing/riskReview
    R->>B: 风控首次业务写操作或确认
    B->>D: 同一事务自动领取risk_reviewer并追加修订/意见
    B->>D: 风控确认后置completed/completed
    F->>B: GET /api/v1/reviews/{reviewId}
    B-->>F: 审核结果
```

## 7. 关键流程与异常处理

文件上传时业务后端校验格式、大小、所有者并持久化文件元数据；每次审核必须绑定不可变的 `contractFileId` 和 `fileSha256`。`POST /reviews` 仅创建 `pending/aiReview` 记录；同一业务后端代码库中的轻量数据库任务执行器领取任务并调用AI服务，不引入消息队列或独立AI编排服务。执行器以事务领取任务、在服务重启后恢复未完成任务，并使用稳定的 `requestId` 调用AI。解析失败、OCR不可用、Qwen超时、返回JSON校验失败均写入审核任务失败状态和可读错误码。仅对网络超时、429和可恢复 5xx 重试，禁止对参数错误或结构校验失败盲目重试。

认证使用 Bearer JWT，后端校验签名、过期时间及角色；管理员接口做角色校验。审核资源同时校验角色和 `reviewStage`：法务可查看全部 `legalReview` 待办、风控可查看全部 `riskReview` 待办，但写操作仅允许未领取任务或本人已领取任务；管理员仅查看，不作为审核员。法务在修订要素、修订法务阶段风险、提交法务反馈或法务确认时，风控在修订风控阶段风险、提交风控反馈或风控确认时，均须在首次业务写操作所在事务内自动领取对应任务：reviewer字段为空则以条件更新或行锁写入当前用户；为当前用户则继续；为其他用户则以 `REVIEW_ALREADY_CLAIMED` 拒绝。业务写入失败时领取必须回滚。普通用户仅访问本人合同且不能修改AI初审结果或提交标注。AI初审快照不可变，人工修订追加留痕并记录前后值、操作人、角色和阶段。上传文件按合同所属人授权下载，路径不得由客户端直接指定。日志不得写入密码、JWT、Qwen API Key 或完整敏感合同正文。

## 8. 可扩展性

V0.1 保持单个业务后端和单个 AI 服务，审核任务以数据库状态管理。需要并发扩展时再引入队列/worker；需要对象存储时再替换本地文件适配层。此处不预置微服务注册中心、消息总线或复杂编排，避免超出赛题范围。
